# SDK 商户售价结算

## 两套账

- 平台成本：服务端事件轮询或签名回调 `credits.debited/refunded`，仅记录在 `platform_credit_events`，不影响本地用户余额。
- 用户售价：生成确认时冻结报价与每个 `saleItems` 分项，按 `credits.sale_debited/sale_refunded` 入用户账。
- 模板许可：`credits.license_debited` 直接按事件金额扣用户余额，不属于生成售价结算。

例如平台成本20、用户售价35：平台成本记录为-20，用户流水为-35。0售价明确保留为0；平台0成本也可由独立售价事件结算非0售价。

## 接口链路

SDK保留原 `/open/sdk/generation-quotes/:id` 查询及批准路径，要求完整身份、请求号和冻结售价分项。本地不信任浏览器传入的估价。

纯 API 新请求统一直接调用设计、服装或视频入口，不要求本地用户余额或充值，不进入 SDK 的报价批准链路。平台的可选报价接口仍属于公开协议，需要时由接入方自行调用，本示例不再提供对应业务模式。

为了避免改写历史任务，已记录的旧 API 报价请求仅可按原冻结快照恢复；缺少快照时提示核对原受理状态，不重新报价、不改成新请求。已受理请求返回原保存响应。SDK 的批准、回调和售价结算流程保持。

报价：`quoteId,externalUserId,clientRequestId,estimatedCredits,expiresAt,saleItems:[{itemId,credits}]`，分项金额和必须等于总售价。每次报价和分项保存在独立SQLite表；同一请求的冻结售价不可覆盖。

售价事件：`settlementId,quoteId,clientRequestId,itemId,taskNo,amount`；退款另有`originalDebitId`。稳定结算号为 `sale:<itemId>:debit/refund`。退款金额须等于原分项售价，部分失败按对应失败分项退款，不做比例分摊。分镜预付转移后任务号可以变化，退款只依赖原分项/扣费关联。

## 幂等、乱序与旧记录

- 原始请求验签和5分钟时间窗保持；结算号、事件号、身份和内容同时校验。
- 回调早于本地报价或退款早于扣费：持久化为PENDING，不改变余额，报价/扣费到达后同一事务处理。
- 下载图片的生成回调与用户售价回调相互独立；图片保存成功不代表已收到售价事件。
- 保存失败不返回成功；业务事件成功持久化但尚缺关联时可以确认接收，页面显示待关联数量。
- 不读取成本delta推算售价，不按当前配置追算旧账。
- 已受理的请求只返回保存的响应；未确认的请求、缺少冻结售价的 SDK 批准会被拒绝重复发起，需先核对原请求状态。
- 售价相关表由应用启动时创建，不会改写已有用户或流水。

## 验证

独立内存/临时SQLite与HTTP替身覆盖：成本20/售价35、0售价、零成本非零售价、修改售价不影响旧单、逐项退款、退款任务号转移、重复事件/结算、错签名、回调先到、重启恢复、A/B隔离、事务故障、超时原请求恢复、旧请求保护。

也可以运行 `node tests/platform-preview.ts --sales`，在 3444 端口打开独立的模拟页面，直观查看售价流水与平台成本的区别。真实售价结算仍需在正式环境实际生成一次后核对。

SDK 批准前在同一 SQLite 事务内冻结报价、计算可用额度并持久预占。可用额度 = 账面余额 − 未收到扣款的预占分项；不同请求不能同时使用同一额度。同报价重试沿用原预占，跨进程批准尝试独立记录，重启后继续保留不确定事实。纯 API 直接生成不创建预占。

售价扣款落账后，该分项在同一事务内不再计入预占；退款仍按原扣款关联记账，不重复预占。全部批准尝试都被明确拒绝且没有结算事实时释放；只要存在在途、成功或不确定尝试就保留。历史报价/批准保守迁移，既有真实扣退不可回滚。

账户页显示账面余额、预占、可用额度及待结算请求，SDK 显示可用额度。已经发生的合法扣款仍按事实记录，不因通知乱序丢弃账务。

**尚待主项目补齐：** 已获批但未提交、部分分项最终不计费的安全释放证明。不能根据本地超时、浏览器关闭或生成终态猜测释放，当前这些未确定分项会保持预占。此项补齐前，不把 SDK 用户余额示例宣称为完整生产结算方案。详见[主项目补正提示词](sdk-reservation-followup.md)。

## 无回调同步

0.4.0 纯 API 可不配回调。后端按用户自适应从 `/open/events` 拉取并逐页处理售价扣退、成本及 API 终态结果；`api_event_cursors` 与 SDK 游标分离。原始事件与接收游标同事务落盘；账务/媒体处理另行标记成功，异常项持久保留并退避重试，不阻塞后续事件。接收游标不代表已结算，沿用原 eventId / settlementId 幂等与退款关联规则。服务关闭后不推进，下次启动恢复。SDK 回调和宿主批准责任保持。
